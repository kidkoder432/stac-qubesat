# QubeSat Flight Software: FSM Spec (DRAFT, needs sign-off)

**Status:** DRAFT. Written from the code as it stands, the original `Qubesat FSM Definition.pdf`, the board backup of `Comms.py`, and the payload ICD. **No part of this has been approved by the team.** **Owner of this document / FSM code:** Prajwal Agrawal

## Why this exists

There was no written spec for how the satellite should behave. The FSM code was inherited with no documentation (last upstream commit \~6 months before this copy was made), and the only design document, `Qubesat FSM Definition.pdf`, is a sketch with most priorities/periods blank and sections that contradict each other. Every number in the code is therefore either from that PDF or was chosen by the implementer. This doc lists them all so they can be confirmed or changed.

Part 7 lists every open question, with the 11 core questions first (7.0). **No answers are proposed.** The "Context" column only explains why the software needs the answer, or what the current code does, so you know what is being asked about; it is not a recommendation and nobody has agreed to it. Please write the decision in the **Answer** column. If the decision belongs to someone else, write who.

## 1\. Overview

Four states. The satellite **boots into IDLE**, deploys its antenna after a wait (both burn wires), then follows a fixed schedule: 14 days of SCIENCE, then repeating 100-minute cycles of 7 COMMS slots and 3 SCIENCE slots (10 minutes each). Comms (radio RX/TX) runs on its own schedule in **every** state; the COMMS *state* is not what enables the radio.

| Code | State   | Purpose                                                                               |
| :--- | :------ | :------------------------------------------------------------------------------------ |
| 0    | STOP    | Not an FSM state. A Comms command: stop transmitting (still listens).                 |
| 1    | IDLE    | Low-power holding state. Beacon \+ battery check. Entered at boot and on low battery. |
| 2    | DEPLOY  | Initialize SD card, fire burn wire (antenna release), then handshake.                 |
| 3    | SCIENCE | Run the payload experiment and log data.                                              |
| 4    | COMMS   | Check solar charging, beacon. (The PDF intends "downlink window"; see Q-C1.)          |

State codes are the same in `StateCodeGenerator.py` and `Comms.py` (a test enforces this). Source for numbering: board backup `Comms.py` (**DECIDED**, as it is what runs on the board).

## 3\. Tasks per state (exactly as in the code)

Lower priority number runs first. `schedule_later=True` means the first run waits one full period.

| 4   | Record to Memory (SD, CSV; sets up the SD card itself if needed; deletes the oldest file only when nearly full) | 10 s     | yes    |
| 5   | Transition Check                          | 10 s     | yes    |
| 6   | Antenna Watchdog                          | 10 min   | yes    |

**COMMS**

| Pri | Task              | Period | Later? |
| :-- | :---------------- | :----- | :----- |
| 1   | Solar Panel Check | 60 s   | no     |
| 2   | Battery Check     | 60 s   | yes    |
| 3   | Beacon            | 30 min | yes    |
| 4   | Transition Check  | 10 s   | yes    |
| 5   | Antenna Watchdog  | 10 min | yes    |

Every state also has a **Radio Health** task (60 s, later) at the lowest priority: it counts consecutive radio errors, re-applies the radio settings after 3, and treats a radio that never recovers as a fault.

The PDF has two conflicting descriptions. Its task list fills in only the idle Beacon (priority 1, 30 min, not later); every other priority/period there is blank. Its sample code is a different design that uses other values (battery check every 5 min, transition check every 60 s, record flush every 30 min, data-packet send every 60 s). The code here follows neither exactly, so apart from the idle Beacon, all periods/priorities are **ASSUMED**. Q-X4 asks which set to use.

## 4\. Ground interface (Comms)

Radio: 433.72 MHz LoRa (team answer, Q-C2), BW 125 kHz, SF7, CR 4/5, sync word 0x12, 5 dBm. Source of the settings: board backup `Comms.py`, configured for TinyGS. Callsign is still a placeholder.

Uplink commands: AES-128-ECB encrypted, CRC-8 \+ complement check.

| Command                                             | Effect                                                                                                                                                                                                                    |
| :-------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SET_STATE(state, lock)`                          | Go to `state`. `lock=1`: FSM transition logic frozen until a command with `lock=0` (or a safety override clears it). `lock=0`: go there, then autonomous transitions resume. The lock is bit 7 of the state byte. |
| `SET_STATE(STOP)`                                 | Comms stops transmitting (keeps listening). FSM state unchanged. Any non-zero state resumes.                                                                                                                              |
| `SET_CONFIG(rx_ticks, tx_packets, telem_cadence)` | Change the RX/TX schedule (persisted in NVM).                                                                                                                                                                             |

The ground repeats a state code for reliability and every copy reaches the FSM. A command for the state the satellite is already in changes nothing (the lock bit is still applied), and NVM is only written when the state code changes. Entering DEPLOY by command re-arms both burn wires even if they gave up before; to re-burn while already in DEPLOY, command another state first.

Downlink: (a) **beacon** every 30 min in TinyGS format (15 bytes: callsign, state, battery mV, temp, mission time, CRC-8); (b) **internal status** packet (18 bytes, first byte `0x03`: state, flags incl. lock/deployed/equipment/ground-heard, burn attempts, battery, temp, mission time, crash count, sweeps completed, next sweep point, payload error count, caught exceptions) every `telem_cadence` TX windows. **Science data is not downlinked yet.**

## 5\. Safety and failure behavior (as implemented)

- **Low battery / overheat → IDLE**, even if the ground locked the state. The lock is cleared when this happens. (Switch: `LOW_BATTERY_OVERRIDES_LOCK`.)
- **Antenna watchdog.** There is no sensor that says the antenna deployed, and if it didn't the ground probably cannot reach us. So: if a burn raised an error, retry every 1 h forever (only the wire that failed); if both wires fired but no ground command has been heard since, re-burn both every 12 h, up to 20 wire burns per boot; stop once any ground command is received after a burn. "Ground heard" is saved to NVM, so a reboot does not re-burn a working antenna. No burn is attempted below 8.0 V.
- **"Deployed" flag** is stored in NVM byte 19 (set once both wires have fired) so a reboot does not re-fire the burn wires. The NVM map is at the top of `QubeSatFSM.py`.
- **SD card failure:** DEPLOY waits (does not proceed without SD). SCIENCE sets up the SD card itself on its first record (a reboot after deploy skips DEPLOY). If the card is nearly full (\< 256 KB) the oldest science file is deleted, never the current one.
- **Watcher.** Every task and the comms tick run in a guard: an exception is logged and counted, not fatal. The same component failing 5 times in a row is a fault and resets the board (`run()` increments `c_state_err`, waits 10 s, resets). The crash count is kept in NVM; after 3 fast crashes in a row the board stops resetting and runs degraded instead of boot-looping, and the count clears after 30 minutes up. There is no hardware watchdog.
- **Mission time** counts seconds since the burn wire first fired (0 before it) and is saved to NVM every 15 minutes in an 8-slot checksummed ring, so a reboot loses at most 15 minutes. Timers (deploy wait, watchdog) use uptime since boot. A ground **lock** is saved to NVM and restored at boot (a locked DEPLOY is not restored, since it would re-burn). The science/comms state is recomputed from mission time after a reboot.

## 6\. Known problems (not spec questions, just bugs/risks)

1. **Burn wire parameters are unconfirmed.** FSM calls `cubesatBurn("1", 0.25, 30)`. `BurnWire` reads the duty cycle as a percent (0.25 → 0.25%), which matches the board library's own `cubesat.burn()`, so that part may be intended (the file's own test comment uses 0.05). What differs from the library call is that `BurnWire` ignores `duration` (always about 350 s, blocking the FSM and radio the whole time). Whether 0.25% for about 6 minutes releases the antenna is unknown. **Needs the burn wire team (Q-D1).**
2. **No flight entry point.** `pycubed/NewCode/bench_main.py` runs the FSM and Comms on the board with the burn wire disabled and short timings (bench only). What else belongs in the flight startup file is Q-X1.
3. Placeholders: callsign `"STAC  "`, AES key all zeros. The burn duty/duration are still the old placeholder values (0.25, 30) until Q-D1 is answered; `BurnWire` still holds each wire for about 6 minutes, so both wires block the FSM and radio for about 12 minutes.
4. Not run on real hardware (except UART). Desktop tests: `pycubed/NewCode/test_fsm.py` (stubs, fake clock).
5. **Possible payload boot hang (unverified).** `payload/src/main.cpp` `setup()` has `while (!Serial) {}` and `platformio.ini` sets `ARDUINO_USB_CDC_ON_BOOT=1`. On the ESP32-S3 this commonly waits for a USB host, so with no USB attached in flight the payload may never finish `setup()`. Needs a test with the payload powered from the battery or a bench supply and no USB host.
6. **RTD reads turn on the 5 V rail.** `sendRTDData()` in `payload/src/command_interface.cpp` switches the 5 V rail on if it is off. A continuous temperature check therefore either keeps 5 V on or power-cycles it. This affects the power budget (Q-P5, Q-P7).
7. **Comms treats fresh or corrupt NVM as STOP.** `_nvm_read_state()` returns 0 when the stored state is blank or corrupt, so a satellite launched with erased NVM would not transmit until commanded. Intended? Comms owner to confirm; `bench_main.py` forces IDLE on the bench.
8. **Hardware import (fixed in code, verify on the board).** The FSM and BurnWire imported `lib.pycubed` and Comms imported `pycubed`; both names load the library twice on the board and the second copy cannot get the pins. All modules now import `cubesat` from `hardware.py`.
9. **NVM wear is not verified.** The mission-time ring writes every 15 minutes (96 writes a day over 8 slots). The SAMD51 NVM size and endurance on this board have not been checked (`len(microcontroller.nvm)` on the REPL gives the size).
10. **Payload side:** the TESTING flag in `payload/src/main.cpp` must be 0 for flight; with it 0 the firmware still has `Serial.print` calls, which should be tested with no USB host for stalls.
